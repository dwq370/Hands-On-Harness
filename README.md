# Hands-on Harness

面向 Agent Harness 的系统性知识与实践整理，用于后续学习与工程落地。

## 项目简介

本项目用于整理 Agent Harness 相关的知识与实践经验，目标不是堆叠资料，而是把碎片化的知识点组织成一张**有深度的知识网络**。每一个知识点都应当回答四个问题：

- 它为什么存在（解决了什么本质问题）？
- 它如何工作（核心机理）？
- 它与哪些技术相邻、替代或互补（网络关系）？
- 它的边界与代价是什么（适用条件、不适用场景、权衡）？

这里的 Harness，指包在模型外面的运行时：执行循环、工具、上下文、状态、钩子和评估。模型负责下一次推断；Harness 决定这次推断如何变成多步、可恢复、可约束的行动。

## 为什么做这件事：Agent 时代的判断力

在 Agent 能够快速生成代码与方案的时代，"获取答案"的成本急剧下降，但"判断方案是否成立、是否适配当前任务"的能力反而容易被稀释。Agent Harness 恰好是一个判断力极其关键的领域：

- 测到的成绩属于**模型与 Harness 的配对**。工具格式、技能加载、压缩策略一变，同一模型的表现可以明显移动；
- 同一个机制在不同任务上收益可能相反（例如技能注入、更长上下文、自动续跑）；
- 大量流行说法把框架、脚手架、平台和 Harness 混称，脱离运行时职责的"最佳实践"往往不成立。

因此本项目坚持：**原理优先、边界清晰、代价明确**。只有理解了机理与约束，人才能在 Agent 给出运行时方案时独立判断，而不是盲从。

## 设计原则

1. **原理驱动** —— 先讲清"为什么"，再谈"怎么做"。
2. **建立关联** —— 每个知识点标注它与上下游职能、替代方案的连接。
3. **明确边界** —— 说明适用条件、不适用场景、代价与权衡。
4. **可验证** —— 尽量提供可对照的轨迹字段、配置与最小实验。
5. **持续演进** —— 与模型、工具协议、产品 Harness 的版本共同更新。

## 目录结构

```text
Hands-On-Harness/
├── 基础概念/              # 定义、相邻概念、谱系、三代工程
├── 运行时/
│   ├── 架构/              # 一步执行、职能依赖、任务压力、循环的形式性质
│   ├── 执行循环/          # 阶段、终止、错误恢复、续跑
│   ├── 工具/              # 契约、通用执行、技能、结果回注
│   ├── 上下文/            # 视图与预算、腐烂、压缩、检索注入
│   ├── 状态/              # 检查点、记忆、提交点、多执行者一致性
│   ├── 钩子/              # 拦截点、确定性检查、批准
│   └── 评估/              # 轨迹、判定层次、测量失真
├── 控制面/
│   ├── 环境与沙箱/        # 工具链、隔离、复位
│   ├── 可观测性/          # 轨迹与跨度、采集边界
│   ├── 治理与安全/        # 注入、权限、审计
│   └── 编排/              # 长程执行、委托、协作形状
├── 工程实践/              # 从行为反推、失败目录、编码 Agent、改进闭环
└── 生态/                  # 系统分类、协议、开放问题
```

脊柱是六个运行时职能 \(H = (E, T, C, S, L, V)\)：执行循环、工具注册表、上下文管理、状态存储、生命周期钩子、评估接口。控制面是同一套职能在环境、观测、治理和编排上的投影。两套公开分类（ETCSLV 与 ETCLOVG）的字母并不相同，对照放在基础概念中，后文避免只靠字母指称。

## 知识网络

各领域并非孤立。理解它们之间的依赖，才能判断一次失败该改模型、改提示，还是改运行时。

```text
基础概念
   │  划定对象：模型推断之外，谁在运行时把行动管住
   ▼
运行时（执行循环 / 工具 / 上下文 / 状态 / 钩子 / 评估）
   │                      │
   │  一步：组视图 → 推断 → 执行 → 提交
   │                      │
   │                      ├──────────► 控制面
   │                      │             环境约束工具真正能做什么
   │                      │             治理通过钩子生效
   │                      │             观测把证据交给评估
   ▼                      ▼
工程实践 ◄────────────── 生态
   失败先归到职能            协议只标准化了部分边界
   编码任务把六列都推高        缺契约的地方每家仍自建
```

- **基础概念**决定后文用词。框架回答如何组装，Harness 回答运行时如何被管住；
- **运行时**是脊柱。上下文提供这一步的视图，循环决定继续或停止，工具产生副作用，状态留下恢复点，钩子在边界上执行规则，评估把过程变成可比较的轨迹；
- **控制面**不另起一套智能。环境、观测、治理、编排是上述职能在部署和协作中的投影；
- **工程实践**把事故和编码场景收回到具体职能，避免只改提示；
- **生态**说明现有系统和协议各补上了哪一格，以及哪些格还没有公共契约。

## 使用方式

1. 先按索引选定主题，读该篇的**原理**，再看**机理**、**关联**与**代价**；
2. 排障时先到「失败目录」和「完备性核对」，确认缺的是哪一个职能，再进入对应文档；
3. 涉及模型、工具格式、隔离级别的结论，核对文内前提，而不是直接采信分数。

## 贡献指南

- 新增文档请放入对应目录，并在本索引中把 `待补充` 换成文件链接；
- 文档遵循「原理 → 机理 → 关联 → 边界与代价」：先写为什么存在，再写核心机理，然后标明网络位置，最后写适用条件、不适用场景和权衡；
- 开篇用一句话总结，并写明结论依赖的模型、协议或产品版本；
- 能对照轨迹、配置或最小实验验证的，一并写上。
