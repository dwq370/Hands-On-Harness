# Hands-on Harness

面向 Agent Harness 的系统性知识与实践整理，用于后续学习与工程落地。

## 项目简介

本项目整理 Agent Harness 的概念、机制与工程实践，并把分散材料组织成可互相引用的知识网络。每一篇需要回答四个问题：

- 它为什么存在（解决了什么本质问题）？
- 它如何工作（核心机理）？
- 它与哪些技术相邻、替代或互补（网络关系）？
- 它的边界与代价是什么（适用条件、不适用场景、权衡）？

这里的 Harness，指包在模型外面的运行时：执行循环、工具、上下文、状态、钩子和评估。模型负责下一次推断；Harness 决定这次推断如何变成多步、可恢复、可约束的行动。

## 编写目的

Agent 可以快速给出实现方案，方案是否成立取决于运行时条件。Agent Harness 的结论通常绑定具体配置：

- 公开分数描述的是模型与 Harness 的联合配置。工具格式、技能加载和压缩策略改变后，同一模型的结果可以明显变化；
- 同一机制的收益随任务变化。技能注入、更长上下文和自动续跑都存在正例与负例；
- 框架、脚手架、平台和 Harness 指称不同层次。脱离运行时职责的建议难以复用。

因此文档要求写明原理、适用边界和代价，使读者能够根据轨迹、配置和任务类型检验方案。

## 设计原则

1. **原理驱动** —— 先讲清"为什么"，再谈"怎么做"。
2. **建立关联** —— 每个知识点标注它与上下游职能、替代方案的连接。
3. **明确边界** —— 说明适用条件、不适用场景、代价与权衡。
4. **可验证** —— 尽量提供可对照的轨迹字段、配置与最小实验。
5. **持续演进** —— 与模型、工具协议、产品 Harness 的版本共同更新。

```text
Hands-On-Harness/
├── 基础概念/              # 定义、相邻概念、历史演进
├── 运行时/
│   ├── 架构/              # 一步执行、职能依赖、任务压力、循环的形式性质、产品结构差异

│   ├── 状态/              # 检查点、记忆、提交点、多执行者一致性
│   ├── 钩子/              # 拦截点、确定性检查、批准
│   └── 评估/              # 轨迹、判定层次、测量失真
├── 控制面/
│   ├── 环境与沙箱/        # 工具链、隔离、复位
│   ├── 可观测性/          # 轨迹与跨度、采集边界
│   ├── 治理与安全/        # 注入、权限、审计
│   └── 编排/              # 长程执行、委托、协作形状
├── 工程实践/              # 从行为反推、失败目录、编码 Agent、改进闭环
└── 生态/                  # 系统分类、协议、开放问题
```

\(H = (E, T, C, S, L, V)\) 是 Agent Harness 产品的质量与成熟度评估框架。六个维度依次为执行循环、工具注册表、上下文管理、状态存储、生命周期钩子和评估接口。评估某一产品时，每一维取三档之一：已具备、部分具备、调用方补齐。六维均达到生产所需的可靠性时，该产品记为成熟的全栈 Harness。环境、观测、治理和编排是上述维度在部署中的落点。公开分类 ETCLOVG 使用部分相同字母，所指层次不同；对照见 [Harness 概念边界](基础概念/Harness概念边界.md)。后文使用中文名称。

## 知识网络

各目录描述同一系统的不同切面。失败定位时，需要先确定证据落在模型、提示、上下文还是运行时控制上。

```text
基础概念
   │  规定术语：模型完成推断，运行时控制多步行动
   ▼
运行时（执行循环 / 工具 / 上下文 / 状态 / 钩子 / 评估）
   │                      │
   │  一步：组视图 → 推断 → 执行 → 提交
   │                      │
   │                      ├──────────► 控制面
   │                      │             环境限定工具的实际权限
   │                      │             治理经钩子执行
   │                      │             观测向评估提供证据
   ▼                      ▼
工程实践 ◄────────────── 生态
   失效按职能归类            协议覆盖部分边界
   编码任务同时提高六维要求    尚无契约的部分由各实现规定
```

- **基础概念**规定后文术语。框架描述开发时的组装方式，Harness 描述运行时的控制方式；
- **运行时**按一次执行的数据流组织：上下文提供当步视图，循环决定继续或停止，工具产生副作用，状态保存恢复点，钩子在边界执行规则，评估把过程写成可比较的轨迹；
- **控制面**描述上述职能在部署中的落点，包括环境、观测、治理和编排；
- **工程实践**把失效和编码场景映射回具体职能；
- **生态**记录现有系统与协议已经覆盖的契约，以及仍由各实现自行规定的部分。

## 使用方式

1. 按索引选定主题，先读该篇的原理，再读机理、关联与代价；
2. 排障时先到「失败目录」和「完备性核对」，确认缺的是哪一个职能，再进入对应文档；
3. 引用涉及模型、工具格式或隔离级别的结论时，核对文内给出的实验前提。

## 贡献指南

- 新增文档请放入对应目录，并在本索引中把 `待补充` 换成文件链接；
- 文档遵循「原理 → 机理 → 关联 → 边界与代价」：先写为什么存在，再写核心机理，然后标明网络位置，最后写适用条件、不适用场景和权衡；
- 开篇给出摘要，并写明结论依赖的模型、协议或产品版本；
- 能对照轨迹、配置或最小实验验证的，一并写上；
- 正文使用书面技术中文：句子完整，术语先定义后使用。避免口语讲解、口号式断句和未定义的比喻。
